# 0002 — Хостинг бэкенда

Статус: принято (2026-07-22)

## Контекст

Бэкенд livescribe (Fastify + WebSocket, релей аудио в Deepgram) нужно вынести с localhost
на удалённую тачку — под расширение, а затем лендинг и админку (ADR-0003, single-port).
Нагрузка лёгкая: STT и анализ внешние (Deepgram / LLM-API), сам сервер — I/O-bound релей +
раздача SPA + будущий Postgres. Расширение работает на HTTPS-страницах (Meet/Zoom/Teams),
поэтому подключение к бэкенду обязано быть `wss://` (браузер блокирует `ws://` с HTTPS) —
нужен домен и TLS, голого IP недостаточно. Ресёрч провайдеров — в истории; вы уже используете
Yandex Cloud (expeditor на `158.160.x`).

## Решение

- **Провайдер: Beget** (beget.com) — крупный российский хост, RU-локации (СПб/Москва/
  Новосибирск) → чисто по 152-ФЗ; оплата в рублях/РФ-картами; лучшая репутация из
  рассмотренных (4.5/5, ~5100 отзывов), эталонная панель, 30-дневный триал. Дешевле Yandex,
  при этом есть managed-экосистема (облачные БД, S3) на будущее.
- **VPS:** Ubuntu LTS, 2 vCPU / 4 ГБ / ~20 ГБ NVMe, локация **Москва**. Публичный **IPv4 —
  отдельная опция ~150 ₽/мес** (IPv6 бесплатно). Отдельная тачка под livescribe.
- **Домен:** отдельный домен под продукт; бэкенд — на поддомене (`api.skribo.ru`),
  лендинг/админка — на основном (ADR-0003, single-port).
- **TLS: Caddy** как reverse-proxy — авто-Let's Encrypt, терминирует HTTPS/WSS, проксирует
  `/ws` (и позже `/api`, статику) на бэкенд.
- **Процесс: systemd**-сервис бэкенда (автоперезапуск), а не tmux.
- **Postgres — на этой же ВМ** (managed-БД у бюджетного VPS нет); аудио — во внешнее
  S3-совместимое хранилище (напр. Yandex/Selectel Object Storage), не на диск ВМ.
- **Деплой:** скилл `deploy` (rsync исходников → сборка на сервере → рестарт сервиса →
  пост-проверка `wss`), по образцу expeditor. Релиз ≠ деплой.

## Последствия

- (+) Недорого (~700–1100 ₽/мес за 2 vCPU/4 ГБ + ~150 ₽ IPv4), RU-латентность и 152-ФЗ (Москва).
- (+) Надёжный провайдер с топовой панелью; есть managed БД и S3 у того же провайдера —
  можно подключить позже вместо self-hosted.
- (+) Caddy снимает возню с сертификатами (авто-обновление TLS).
- (−) На старте Postgres держим на самой ВМ (managed БД — опция на потом); бэкапы/мониторинг
  настраиваем сами.
- (−) Нет консолидации с expeditor (он на Yandex Cloud) — отдельная панель/биллинг.
- (−) IPv4 — отдельная платная строка (~150 ₽/мес).
- Прод-подготовка кода: WS-URL расширения вынесен в конфиг ✅; осталось сузить CORS до
  origin расширения при деплое.

## Итоговый выбор доменов (2026-07-23)

Продукт переименован в **Skribo** (ADR-0004). Домены:

- **API сейчас: `api.skribo.ru`.** `skribo.ru` регистрируется у RU-регистратора
  (reg.ru/2domains, ~150–200 ₽, рублями). A-запись `api.skribo.ru` → публичный IP ВМ.
- **Бренд-домен позже: `skribo.io`** (свободен) — под лендинг/админку; регистрация на
  Porkbun (~$41/год, иностранная карта есть). Берётся к моменту публичного бренда.
- **`.space` рассмотрен** (свободен, рублями у reg.ru) — отклонён как основной бренд
  (перцепция «бюджетный»), для API не нужен, т.к. `.ru` дешевле и проще.

Код-подготовка (сделано): WS-URL расширения вынесен в build-time конфиг (Vite `define`
`__WS_URL__`, дефолт `ws://localhost:3001/ws`; прод — `WS_URL=wss://api.skribo.ru/ws`).

## Рассмотренные альтернативы

- **Yandex Cloud** — премиум + консолидация с expeditor + managed Object Storage/Postgres,
  но ~2032 ₽/мес (2 vCPU 20%/4 ГБ) — отклонено по цене (~в 3 раза дороже AdminVPS).
- **AdminVPS** — чуть дешевле, тоже RU/Москва, 4.4/5; Beget выбран за большую репутацию
  (~5100 отзывов), 30-дневный триал, панель и managed БД/S3 на будущее.
- **Fornex** — дёшево, есть ДЦ Москва, но HQ в Испании и оплата картой РФ под вопросом (крипта).
- **4vps.su** — дешевле, но бюджетно-реселлерский профиль; для прод-данных менее надёжен.
- **Selectel / Aeza** — сопоставимые RU-варианты.
- **Hetzner (ЕС)** — лучший ценник, но оплата из РФ, латентность к RU и 152-ФЗ — плохо
  под хранение переговоров.
- **Co-locate на ВМ expeditor** — отклонено: связывает два продукта на одной тачке.
- **Голый IP без домена** — невозможно: расширение на HTTPS требует `wss://` с валидным TLS.
