# Дизайн: нормальный логин в расширении (LS-11)

Дата: 2026-07-24
Статус: согласован (ожидает вычитки спеки)

## Контекст и цель

Сейчас привязка расширения к аккаунту — ручная: пользователь копирует персональный токен из
кабинета и вставляет в поле встроенного виджета. Неудобно. Цель — убрать копипаст: логин
живёт в расширении, и в идеале расширение само подхватывает сессию кабинета.

Технический факт: WS идёт на `api.skribo.ru`, а cookie-сессия кабинета — host-only на
`app.skribo.ru`. Cookie на WS (`api.skribo.ru`) не долетит, поэтому привязка WS-сессии всё
равно через **токен** (`token` в `start`-сообщении, механизм уже есть). «Авто-подхват» =
расширение, увидев сессию кабинета, само тихо получает токен.

## Согласованные решения

1. **Гибрид:** авто-подхват сессии кабинета когда работает (лучший UX) + fallback
   email+пароль прямо в расширении. Ручного копирования токена нет.
2. **UI — отдельный попап расширения** (клик по иконке в тулбаре), не встроенный виджет.
3. WS-привязка остаётся токеном в `start` (не трогаем offscreen/service-worker wiring,
   который уже читает `skriboToken` из `chrome.storage.local`).

## Архитектура

### Попап (`packages/extension/src/popup/`)
- React + Vite (доп. entry в `vite.config.ts`); `action.default_popup: "popup.html"` в manifest.
- Состояния: **загрузка** → **вошёл** («Вошли как <email>» + «Выйти», ссылка «Открыть кабинет»)
  / **гость** (форма email+пароль + ссылка «Регистрация в кабинете» на `https://app.skribo.ru`).
- При успехе (любой путь) сохраняет WS-токен в `chrome.storage.local` (`skriboToken`) и статус
  (`skriboAccountEmail`). «Выйти» — очищает их (+ best-effort logout).

### Гибридный флоу (в попапе/service-worker)
1. **Авто-подхват:** `GET https://app.skribo.ru/api/auth/me` с `credentials:'include'`.
   Если 200 → `POST https://app.skribo.ru/api/auth/extension-token` (по cookie) → `{ token }` →
   сохранить `skriboToken`, показать «вошли (через кабинет)».
2. **Fallback:** если 401/недоступно → форма → `POST https://api.skribo.ru/api/auth/extension-login`
   `{ email, password }` → `{ user, token }` → сохранить.

### Бэкенд (`packages/backend`) — 2 эндпоинта
- `POST /api/auth/extension-token` — cookie-authed (`requireUser`). Возвращает `{ token }` —
  персональный токен текущего юзера: **переиспользует** существующий токен с меткой
  `extension`, иначе создаёт. (Чтобы не плодить токены при каждом открытии попапа. Т.к. в БД
  хранится только `tokenHash`, «переиспользование» = не создавать новый, если у юзера уже есть
  токен с label `extension`; при отсутствии — создать и вернуть сырой один раз. Нюанс: если
  токен уже есть, сырой недоступен → тогда создаём новый с label `extension`, старый удаляем
  (ротация), чтобы всегда вернуть рабочий сырой токен. Итог: у юзера всегда ≤1 `extension`-токен.)
- `POST /api/auth/extension-login` `{ email, password }` — проверка bcrypt; на успех — та же
  логика получения `extension`-токена → `{ user: {id,email,name}, token }`. 401 при неверных.
- Оба переиспользуют `verifyPassword`/`generateToken`/`hashToken` и модель `PersonalToken`.
- CORS не меняем: extension-запросы к хостам из `host_permissions` не подчиняются CORS.

### Manifest
- `action.default_popup: "popup.html"` (+ иконка действия при наличии).
- `host_permissions`: добавить `https://app.skribo.ru/*` и `https://api.skribo.ru/*`
  (чтобы extension-fetch слал cookie / читал ответ).
- Убрать поле ручного токена из встроенного виджета (`content.ts`); чтение `skriboToken` в
  service-worker/offscreen — без изменений.

## Риск и его митигация
Сработает ли авто-подхват — зависит от того, отдаёт ли Chrome (MV3) httpOnly-cookie
`app.skribo.ru` extension-запросу с `credentials`. Поведение в свежих Chrome неустойчивое.
**Гибрид деградирует мягко:** при неудаче авто-подхвата — форма логина (fallback) работает
всегда. На реализации проверить авто-подхват в реальном Chrome; если не работает — fallback
основной, авто-подхват best-effort (не блокирует MVP).

## Последовательность реализации (под-планы)
1. **Бэкенд:** `extension-token` + `extension-login` (+ unit-тест логики получения/ротации
   токена и проверки пароля). Ручная curl-проверка обоих.
2. **Расширение:** попап (Vite entry + manifest `action` + `host_permissions`) + auth-UI +
   гибридный флоу + сохранение токена; убрать поле токена из виджета.
3. **Сквозная проверка:** оба пути (авто-подхват при залогиненном кабинете; fallback-логин),
   затем запись → встреча в кабинете.

## Границы (YAGNI)
- Без OAuth/Google в расширении (позже).
- Без регистрации в расширении — только вход; регистрация — ссылкой в кабинет.
- Не трогаем WS/offscreen/audio, кроме удаления поля токена из виджета.

## Критерии готовности
- Попап: залогинен в кабинете → авто-«вошли» (если Chrome отдаёт cookie) ИЛИ форма → вход по
  email+паролю → «вошли»; токен сохранён; «Выйти» очищает.
- Запись из расширения после логина → встреча появляется в кабинете (сквозняк).
- Поле ручного токена из виджета удалено; type-check/build зелёные.
