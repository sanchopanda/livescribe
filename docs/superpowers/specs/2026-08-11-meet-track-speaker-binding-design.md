# Привязка WebRTC-дорожки к участнику Meet (дизайн)

Дата: 2026-08-11. Статус: согласован владельцем.
Задача бэклога: **LS-35, пункт 2** (пункт 1 закрыт коммитом `4d901ed`). Доска: карточка #58.

## Задача

В per-track на Meet речь всех участников записывается (пункт 1), но подписана технически:
`Participant f8d37a39`. Нужны человеческие имена.

Прочитать имя — не проблема: `getMeetActiveSpeaker` после LS-33 надёжно отвечает, **кто говорит
сейчас**. Проблема — связать это имя с конкретной аудиодорожкой: у дорожки есть `trackId`
(`33f1a44f-…`) и номер потока (`6666`), и ни один элемент DOM Meet этих значений не содержит.

## Почему нет детерминированного пути

Проверено на живом звонке 11.08, а не предположено:

- **ssrc → плитка.** Скан 1283 элементов (не усечён): ssrc `6666`/`6667` найдены только на
  **наших** элементах реестра. У Meet `data-ssrc` в DOM отсутствует.
- **id потока → участник** (приём, которым живёт Pachca: `data-stream-id` → endpoint → плитка
  `participant_<endpoint>`). У Meet `event.streams[0].id` — это ssrc, идентификатора участника в
  нём нет.
- **Медиа внутри плитки.** Совпадение `srcObject` работало бы при включённых камерах, но на
  рабочих звонках камеры выключены, и внутри плитки нет ни одного медиаэлемента.
- **Разметка плитки.** В блоке управления плиткой есть только имена (три `aria-label`) и
  `jslog`-идентификаторы UI-логирования. Связки с дорожкой нет.

Сопоставление «слот RTP ↔ участник» живёт во внутренней модели Meet и в атрибуты не выводится.
Чтение внутреннего состояния js-контроллеров отвергнуто: ломается на каждом релизе Meet и не
поддаётся отладке вслепую.

## Решение

Подсветка плитки как сигнал + память привязки. Наблюдение «говорит один участник, энергия ровно
на одной дорожке» закрепляется как факт «дорожка = участник», и дальше имя берётся из памяти, а не
из момента.

Память здесь — не украшение. Наивный вариант «имя из подсветки на каждый чанк» ломается там, где
per-track как раз и должен выигрывать: при одновременной речи двух дорожек обе получат одно имя, а
на стыках реплик подписи съедут из-за задержки индикатора. Это в точности класс дефекта LS-28.

### Модуль

`packages/extension/src/content/platforms/meet/audio/per-track/speaker-binding.ts` — без DOM и без
WebRTC, поэтому тестируется в node-окружении, как `capture-targets.ts` и `active-speaker-dom.ts`.

Интерфейс:

```ts
export interface TrackEnergy { trackId: string; rms: number }
export interface BindingObservation {
  tracks: readonly TrackEnergy[];
  domSpeaker: { participantId: string; speaker: string | null } | null;
  mutedParticipantIds?: readonly string[];
  now: number;
}
export interface BindingChange { trackId: string; participantId: string; speaker: string }

export class TrackSpeakerBinding {
  observe(observation: BindingObservation): BindingChange[]; // подтверждённые привязки за этот такт
  speakerFor(trackId: string): string | null;
  reset(): void;
}
```

`observe` возвращает **только новые подтверждения** — вызывающая сторона по ним решает, что
отправить на бэкенд.

### Правило

1. Наблюдение учитывается, только если DOM даёт ровно одного говорящего **и** ровно одна дорожка
   выше порога энергии. Локальная дорожка при этом подсчёте не участвует вовсе: собственная речь
   не должна лишать наблюдение годности, иначе на любой реплике владельца записи привязка
   остальных перестаёт набираться. Порог — тот же, что у VAD (`per-track/core/vad.ts`), чтобы
   «есть речь» означало одно и то же в захвате и в привязке.
2. Замьюченные участники исключаются из кандидатов: у них речи быть не может. Состояние берётся из
   `aria-label` кнопки микрофона плитки. Фильтр необязательный — при неудачном чтении просто не
   применяется.
3. Три согласных наблюдения → привязка подтверждена. Счётчик накопительный, наблюдения не обязаны
   идти подряд; несогласное наблюдение обнуляет счётчик согласий для этой пары.
4. Один участник = одна дорожка: новая привязка снимает прежнюю для того же участника.
5. Три несогласных наблюдения по подтверждённой дорожке → привязка сброшена, набирается заново
   обычными тремя согласными. Несогласия считаются **по конкретному участнику**: три шумных чтения,
   назвавшие трёх разных людей, в сброс не складываются, иначе шум подписал бы реплику чужим
   именем. Сами промахи в зачёт новому участнику не идут — по той же причине.
   Это переезд слота: Meet держит пул приёмных слотов (наблюдали 4 слота на 3 участников, два с
   нулевой энергией) и переиспользует их.
6. Локальная дорожка в корреляции не участвует — у неё имя «Вы» из `SELF_OWNER`.
7. Все пороги — константы в одном месте модуля: их придётся крутить по живым звонкам.

### Интеграция

Вперёд имя уже доезжает, достраивать нечего: транскрайбер отправляет `speaker` с каждым чанком,
бэкенд обновляет запись участника (`websocket/handler.ts:518`), следующие финалы приходят с именем.
Транскрайбер уже считает RMS каждого чанка в `sendChunkToOffscreen`, а DOM-детектор уже опрашивается
в `content.ts` — новых источников данных не нужно, нужна их встреча в одном месте.

### Переименование задним числом

Реплики, записанные до подтверждения, должны получить имя — иначе начало каждого звонка остаётся
безымянным.

1. Клиент → сервер: `rename_participant { sessionId, participantId, speaker }`.
2. Бэкенд обновляет имя участника в сессии и выполняет
   `UPDATE TranscriptSegment SET speaker = <имя> WHERE meetingId = ? AND speaker = <прежняя
   техническая подпись>`. Миграция не нужна: в `TranscriptSegment` нет `participantId`, но
   техническая подпись (`Participant f8d37a39`) уникальна для дорожки в пределах встречи.
   **Селектором может быть только техническая подпись.** Второе переименование той же дорожки
   приходит, когда Meet отдал слот другому участнику, и там прежняя подпись — настоящее имя живого
   человека; такой `UPDATE` переписал бы его подлинные реплики на чужое имя без возможности
   восстановить атрибуцию. Поэтому: подпись в памяти обновляется всегда (следующие финалы идут под
   новым именем), а задним числом правится ровно один раз — с технической подписи на имя.
3. Сервер → клиент: `participant_renamed { participantId, speaker }`; виджет переписывает подписи
   уже показанных реплик.

## Чего сознательно не делаем

- Не трогаем Pachca: там детерминированный путь работает, и общий модуль сейчас был бы абстракцией
  над одним случаем.
- Не добавляем колонку `participantId` в `TranscriptSegment`: без неё обходимся.
- Не мостим привязку через видео (работает только при включённых камерах).
- Не включаем диаризацию STT: ADR-0001 оставляет Deepgram единственным провайдером, а диаризация
  архивирована в `docs/SPEAKER_DETECTION_ARCHIVE.md`.

## Тесты

Юнит на модуле привязки, на данных живого звонка: подтверждение после трёх наблюдений; отсутствие
подтверждения при двух одновременно активных дорожках; отсутствие подтверждения, когда DOM молчит;
переезд слота (сброс и перенабор); один участник не может держать две дорожки; замьюченный участник
не становится кандидатом.

Бэкенд: тест переименования — сегменты с технической подписью получают имя, чужие встречи не
задеты.

Браузерная проверка за владельцем: на звонке с выключенными камерами реплики всех участников
получают имена, начало звонка переименовывается задним числом.

## Риски

- **Долгий набор привязки на шумном звонке.** Строгое правило ждёт чистого момента. Гасится
  переименованием задним числом: имя доедет до всех реплик дорожки.
- **Ошибка привязки при эхе из колонок.** Чужой голос из динамиков поднимает энергию на локальной
  дорожке; локальная дорожка в корреляции не участвует, поэтому на чужие привязки это не влияет.
- **Обфускация Meet.** Сигнал подсветки читает `active-speaker-dom.ts`, где уже есть защита: при
  устаревшем маркере детектор отвечает «не знаю», и привязка просто не набирается — вместо
  уверенно неверных имён.

## Готово, когда

На звонке с выключенными камерами в per-track реплики всех участников подписаны именами; реплики,
записанные до подтверждения, переименованы и в виджете, и в транскрипте кабинета; юнит-тесты
покрывают правило и переименование.
